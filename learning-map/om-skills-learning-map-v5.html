1

Zrób zmianę i opublikuj branch

robi: om-check-and-commit
/om-check-and-commit albo zdaniem: „Use om-check-and-commit to verify and commit the current changes"
Warunek wstępny
Jesteś na feature branchu, zmiany w drzewie roboczym.
Co się dzieje
Uruchamia validation.commands, naprawia proste błędy, commituje i pushuje.
Zwraca
SHA commita + nazwę brancha; ustawia upstream.
Weryfikacja
git log --oneline -1 oraz branch widoczny na GitHubie.
Kiedy pominąć: jeśli od razu idziesz do /om-open-pr — on też commituje i pushuje. Dwa skille pod rząd potrzebne są tylko wtedy, gdy chcesz publikować branch bez otwierania PR.
2

Otwórz PR z pełnym zestawem labeli

robi: om-open-pr
/om-open-pr issue-driven: /om-open-pr <issueId> — wtedy dokłada linkowanie i zwalnia locka na Issue
Warunek wstępny
Branch istnieje; PR dla niego jeszcze nie istnieje (skill i tak sprawdza).
Co się dzieje
Otwiera ready (nie draft) PR do main, nakłada 5 labeli + komentarz z uzasadnieniem.
Zwraca
PR: #<n> (link: …) — to jest input następnego kroku.
Weryfikacja
gh pr view <n> --json labels,isDraft

Review — i ewentualnie autofix

robi: om-auto-review-pr (silnik: om-code-review)
/om-auto-review-pr <nr> cudzy PR, który ma zostać naprawiony: /om-auto-review-pr <nr> --autofix
Warunek wstępny
PR otwarty i nieprzejęty przez innego agenta.
Co się dzieje
Claim → izolowany worktree → gate → checklisty → werdykt → label → zwolnienie locka → sprzątanie.
Zwraca
APPROVED lub CHANGES REQUESTED + PR:; przy autofixie także SHA commitów naprawczych.
Weryfikacja

⏸ Autofix nie zawsze rusza: pętla naprawcza działa tylko na Twoim własnym PR albo z flagą --autofix. Na cudzym PR bez flagi skill zrobi review i odda PR autorowi — nie dotknie brancha.

Re-review po każdej zmianie HEAD

robi: om-auto-review-pr · decyduje: człowiek
/om-auto-review-pr <nr> ten sam skill; wykrywa, że to re-review, i re-sprawdza poprzednie findings
Warunek wstępny
Po poprzednim review pojawiły się nowe commity.
Co się dzieje
Tytuł raportu Re-review:, sprawdzenie każdego wcześniejszego findingu, świeży werdykt.
Zwraca
Nowy werdykt zakotwiczony w aktualnym SHA.
Weryfikacja
Porównaj SHA z raportu z gh pr view <n> --json headRefOid.
⏸ Pułapka, w którą wpadliśmy dwa razy: approve dotyczy konkretnego SHA. Każdy push dezaktualizuje werdykt, a label merge-queue zostaje — więc wygląda na aktualny, choć opisuje starszy commit. PR #5 mergował się jako 6c4dea7, mając approve z 6719890.
5

Merge z kontrolą bramek

robi: om-approve-merge-pr · zgoda: człowiek
/om-approve-merge-pr <nr> z follow-upem: „…and add a follow-up: <treść>" — issue powstaje dopiero po udanym merge'u
Warunek wstępny
PR otwarty, bez twardych blokad, konflikt rozwiązany.
Co się dzieje
Sprawdza blokady i QA gate, próbuje approve, robi squash merge.
Zwraca
SHA merge commita + potwierdzenie usunięcia brancha, jeśli o to poprosisz.
Weryfikacja
git log origin/main --oneline -1
⏸ Tu pipeline zawsze pyta w solo-repo: GitHub odrzuca approve na własnym PR. Skill zgłasza to i czeka na Twoją decyzję: merge bez formalnego approve, drugie konto, albo bot. Zdarzyło się na PR #3, #4 i #5 — to nie jest wyjątek, to stały element procesu tutaj.
6

Sync i sprzątanie po merge'u

robi: człowiek · żaden skill tego nie robi
git checkout main && git pull --ff-only && git branch -D <branch> && git fetch --prune sprawdź też: git worktree list i git branch --list 'review/*'
Warunek wstępny
PR zmergowany.
Co się dzieje
Lokalne repo dogania origin/main; znikają martwe refy.
Zwraca
Czysty punkt startu do następnej lekcji.
Weryfikacja
git status mówi „up to date with origin/main".
⚠ Trzy razy z rzędu o tym zapomnieliśmy. Po każdym merge zostawał lokalny branch za origin i skasowany remote. Na Windows katalog worktree potrafi zostać zablokowany („Permission denied" / „Device or resource busy") — wtedy powtórz usunięcie po chwili.
Zasada przekazywania kontekstu: każdy skill kończy raport linią PR: #<n> (link: …) (a przy pracy z ticketu także Issue: #<n>). Dziś Ty przenosisz ten numer do następnej komendy. To dokładnie ten szew, który ma zniknąć w Lesson 5 — szczegóły w sekcji Handoff Contract.

4b. Gates & Checkpoints — co realnie blokuje i gdzie pipeline pyta człowieka

Najtrzeźwiejsza sekcja tej mapy: rygor pipeline'u równa się rygorowi bramek, które faktycznie skonfigurowałeś.

reality check

Validation gate ● aktywna

validation.commands w tym repo to dokładnie jedna komenda: git diff --check. Wyłapuje trailing whitespace i markery konfliktu — nic więcej. Brak buildu, lintera, testów. Konsekwencja: „approve" tutaj jest zdaniem o lekturze diffa, nie o zielonym buildzie, i każdy raport review musi to mówić wprost.

QA gate ○ wyłączona

qaGate: false, więc needs-qa jest tylko doradcze i nie zatrzyma merge'a. Po włączeniu PR z needs-qa nie zmerguje się bez qa-approved, które nadaje wyłącznie tester albo inżynier korzystający z wyjątku self-QA (z dowodem). Twarde blokady działają zawsze: qa-failed, blocked, do-not-merge.

CI / required checks ◌ nie istnieje

Brak katalogu .github/workflows/ — żaden check nie raportuje się na PR-ach, więc nie ma na co czekać i nic nie gatuje merge'a poza labelami. Cała logika ci.maxWaitMinutes, ci-monitoring i follow-upu z wynikiem CI jest opisana, ale ani razu nieuruchomiona.

Branch protection ◌ brak

main nie jest chroniony: gh api …/protection zwraca 404. Dlatego brak formalnego approve nie zablokował żadnego merge'a. To jedyny powód, dla którego limit self-approval był niedogodnością, a nie ścianą.

⏸ Gdzie pipeline zatrzymuje się i pyta człowieka
self-approval
GitHub odrzuca approve własnego PR. om-approve-merge-pr zgłasza to i czeka na decyzję. ● zaobserwowane 3× (PR #3, #4, #5) — w solo-repo to stały punkt procesu.
claim conflict
Jeśli locka trzyma ktoś inny, skill zatrzymuje się i pyta, zamiast nadpisać. Ominięcie wymaga jawnego --force i komentarza z uzasadnieniem. ◌ nietestowane — nie było kolizji.
needs-qa + skip-qa
Sprzeczne labele QA → skill pyta, który jest właściwy, i nie zgaduje. ◌ nietestowane.
changes-requested przy merge'u
Labela sugeruje nieprzerobiony feedback → om-approve-merge-pr prosi o potwierdzenie zamiaru. ◌ nietestowane.
decyzje architektoniczne
Autofix naprawia sam braki testów, lint, typy i drobiazgi, ale zatrzymuje się przy niejednoznacznych decyzjach produktowych, zmianach łamiących kontrakt i braku dostępu do środowiska.
draft PR
Merge skilla nie tknie draftu po cichu — najpierw pyta, czy oznaczyć jako ready. ◌ nietestowane.
Zasada, którą warto zapamiętać: raportowanie jest wczesne, merge nigdy. Skille nakładają labele i publikują review, gdy tylko skończą pracę — nie czekając na CI. Ale merge wymaga, żeby bramki były naprawdę zielone; lokalna walidacja jest dowodem tego przebiegu, nigdy substytutem branch protection.

6a. Handoff contract — czym skille się łączą

Mechanizm, którym jeden skill przekazuje pracę następnemu. Dziś ten szew obsługuje człowiek — kopiuje numer PR do kolejnej komendy.

◌ automatyczny handoff nietestowany

Linie referencyjne

Każdy skill produkujący PR kończy raport dokładnie takim tekstem — parsowanym przez kolejne skille, więc kształt jest sztywny:

PR: #5 (link: https://github.com/…/pull/5) Issue: #2 (link: …) — tylko gdy przebieg ma ticket

To jedyny kanał przekazania kontekstu: nie ma pamięci dzielonej między skillami. Stan pracy żyje w repo i w trackerze, a te linie mówią, gdzie go szukać.

Trzy tryby przekazania

Human relay
● Lessons 1–4 — czytasz PR: #n i wpisujesz numer w następnej komendzie
Lock handoff
○ om-open-pr --handoff <skill> przenosi locka na PR, żeby nie było luki między etapami
Chain driver
◌ skill-orkiestrator (np. om-auto-fix-issue) prowadzi cały łańcuch i sam zwalnia locka na końcu
Dlaczego lock nie jest zwalniany między krokami łańcucha: gdyby zniknął choć na chwilę, inny agent zobaczyłby „nikt nie pracuje" i legalnie zacząłby dublować robotę. Dlatego kontrakt mówi transfer, nie „zwolnij i weź ponownie".
Test do Lesson 5: jeśli handoff działa, po jednym wywołaniu powinny pojawić się kolejno claim na Issue, claim przeniesiony na PR i komentarze kilku różnych skilli — bez ani jednej komendy z Twojej strony pomiędzy nimi.

7a. Corrections log — co zapisałem źle i jak to wyszło

Log nauki jest wart tyle, ile jego wiarygodność. Te wpisy przeszły review, review je obalił dowodem i zostały poprawione — to jest wzorzec, nie wstyd.

● PR #5

1 · Experiment 001 sklejał dwa różne przebiegi

Było: jedna lista obserwacji bez wskazania, skąd pochodzi która — „claim na Issue" obok „odrzucone approve", jakby to był jeden przebieg.
Jest: Goal mówi wprost, że opisane są dwa przebiegi, a bullety noszą swój numer — Issue #2 → PR #3 dla claimu, PR #4 dla reszty.
Jak wyszło: review sprawdziło każdą obserwację osobno i zobaczyło, że przebieg PR #4 nie miał żadnego Issue. Oba zdania były prawdziwe — fałszywa była sugestia, że pochodzą z jednego runu.

2 · „claims prevented concurrent agents" — wniosek bez obserwacji

Było: claimy zapobiegły równoległej pracy agentów.
Jest: claimy były nakładane i zwalniane wokół każdego etapu; to mechanizm, który ma temu zapobiegać, ale kolizji nie było.
Jak wyszło: nikt nigdy nie próbował przejąć tego PR — więc nic nie zostało powstrzymane. Zdanie opisywało intencję projektu jako zaobserwowany skutek.

3 · „Each skill claimed the PR" — nadmierne uogólnienie

Było: każdy skill claimował PR assignee'em, labelą in-progress i komentarzem.
Jest: claimuje tylko om-auto-review-pr; om-open-pr i om-approve-merge-pr działają na PR bez brania locka.
Jak wyszło: timeline PR #4 pokazuje pięć labeli nałożonych bez assignee, a dopiero potem zdarzenie assigned razem z in-progress. Ironia: to zdanie napisał agent, poprawiając poprzedni błąd — dlatego re-review po poprawce nie jest formalnością.
Reguła wyciągnięta z tych trzech: każde twierdzenie w logu musi dać się przypiąć do dowodu — numeru PR, Issue, commita albo timeline'u. Jeśli nie potrafisz wskazać dowodu, wpis należy do ◌ not tested, a nie do ● observed. Sekcja Observed ma dlatego klikalne numery.

8a. Process gaps — kroki, których nikt nie opisał

Luki znalezione praktyką, nie lekturą. Cztery pierwsze to moim zdaniem braki samego SDLC.md, nie tylko tej mapy — kandydaci na osobny PR przez pipeline.

◌ do potwierdzenia w Lesson 5
1 · Nikt nie tworzy brancha ⚠ luka SDLCW przebiegu branch-driven żaden etap nie mówi, kiedy i jak powstaje feature branch. om-check-and-commit commituje „bieżący branch" i nie ma guardu — stojąc na main, scommituje na main. Propozycja: krok 0 „utwórz branch" jako jawny element procesu.
2 · Brak preflightu ⚠ luka SDLCNic nie sprawdza, czy branch wychodzi z aktualnego main, zanim zaczniesz pracę. Przy dłuższej lekcji łatwo pracować na nieaktualnej bazie i dowiedzieć się o tym dopiero przy konflikcie.
3 · Brak synchronizacji po merge'u ⚠ luka SDLC„Post-merge housekeeping" w SDLC.md dotyczy wyłącznie trackera: zamykania issues i follow-upów. O Twoim lokalnym repo nie ma ani słowa — a to tutaj zostaje branch za origin i skasowany remote. Trafiło nas trzy razy z rzędu.
4 · Approve dotyczy konkretnego SHA ⚠ luka SDLCProces mówi „re-reviewed until approved", ale nie mówi, że każdy push unieważnia werdykt, podczas gdy labela merge-queue zostaje i wygląda na aktualną. PR #5 zmergował się jako 6c4dea7 z approve wystawionym na 6719890.
5 · Self-approval nie jest częścią procesuSDLC.md traktuje approve jako krok, który po prostu się udaje. W repo jednoosobowym nie udaje się nigdy. Powinien być opisany jako znany stan z trzema wyjściami: merge bez formalnego approve, drugie konto, albo bot.
6 · Kiedy nie używać skillaNigdzie nie jest napisane, że om-open-pr sam commituje i pushuje, więc om-check-and-commit przed nim bywa zbędny. Przy PR #5 drugi skill nie miał już czego commitować.
7 · Sprzątanie worktree i gałęzi review/pr-*Review działa w izolowanym worktree i zostawia lokalną gałąź, która przeżywa git worktree remove. Na Windows katalog bywa zablokowany („Permission denied" / „Device or resource busy") i usunięcie udaje się dopiero za drugim razem. To zdarzyło się przy każdym review — a nie jest krokiem procesu.
8 · Aktualizacja logów naukiW tym repo EXPERIMENTS.md i FINDINGS.md to realny etap po każdej lekcji — z własnymi konwencjami numeracji i separatorów, które review egzekwuje. Nigdzie nie jest zapisany jako krok.
Co z tym zrobić: punkty 1–4 przetestować w Lesson 5 i jeśli się potwierdzą, dopisać do SDLC.md osobnym PR-em przeprowadzonym przez pipeline — zmiana procesu wykonana przez ten proces jest najlepszym możliwym testem.
