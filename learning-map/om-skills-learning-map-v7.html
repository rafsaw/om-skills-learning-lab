Trzy rzeczy, które łatwo pomylić: merge-queue to routing, a nie dowód QA — PR z needs-qa legalnie tam czeka. Labela qa należy wyłącznie do testera i żaden automat jej nie nadaje. A in-progress to lock, nie stan procesu: ci-monitoring, które go zastępuje po zakończeniu pracy, nie blokuje nikogo — mówi tylko, że wciąż należy się komentarz z wynikiem CI.

4b. Gates & Checkpoints — co realnie blokuje i gdzie pipeline pyta człowieka

Najtrzeźwiejsza sekcja tej mapy: rygor pipeline'u równa się rygorowi bramek, które faktycznie skonfigurowałeś.

reality check

Validation gate ● aktywna

validation.commands w tym repo to dokładnie jedna komenda: git diff --check. Wyłapuje trailing whitespace i markery konfliktu — nic więcej. Brak buildu, lintera, testów. Konsekwencja: „approve" tutaj jest zdaniem o lekturze diffa, nie o zielonym buildzie, i każdy raport review musi to mówić wprost.

QA gate ○ wyłączona

qaGate: false, więc needs-qa jest tylko doradcze i nie zatrzyma merge'a. Po włączeniu PR z needs-qa nie zmerguje się bez qa-approved, które nadaje wyłącznie tester albo inżynier korzystający z wyjątku self-QA (z dowodem). Twarde blokady działają zawsze: qa-failed, blocked, do-not-merge.

CI / required checks ◌ nie istnieje

Brak katalogu .github/workflows/ — żaden check nie raportuje się na PR-ach, więc nie ma na co czekać i nic nie gatuje merge'a poza labelami. Cała logika ci.maxWaitMinutes, ci-monitoring i follow-upu z wynikiem CI jest opisana, ale ani razu nieuruchomiona.

Branch protection ◌ brak

main nie jest chroniony: gh api …/protection zwraca 404. Dlatego brak formalnego approve nie zablokował żadnego merge'a. To jedyny powód, dla którego limit self-approval był niedogodnością, a nie ścianą.

⏸ Gdzie pipeline zatrzymuje się i pyta człowieka
self-approval
GitHub odrzuca approve własnego PR. om-approve-merge-pr zgłasza to i czeka na decyzję. ● zaobserwowane 3× (PR #3, #4, #5) — w solo-repo to stały punkt procesu.
claim conflict
Jeśli locka trzyma ktoś inny, skill zatrzymuje się i pyta, zamiast nadpisać. Ominięcie wymaga jawnego --force i komentarza z uzasadnieniem. ◌ nietestowane — nie było kolizji.
needs-qa + skip-qa
Sprzeczne labele QA → skill pyta, który jest właściwy, i nie zgaduje. ◌ nietestowane.
changes-requested przy merge'u
Labela sugeruje nieprzerobiony feedback → om-approve-merge-pr prosi o potwierdzenie zamiaru. ◌ nietestowane.
decyzje architektoniczne
Autofix naprawia sam braki testów, lint, typy i drobiazgi, ale zatrzymuje się przy niejednoznacznych decyzjach produktowych, zmianach łamiących kontrakt i braku dostępu do środowiska.
draft PR
Merge skilla nie tknie draftu po cichu — najpierw pyta, czy oznaczyć jako ready. ◌ nietestowane.
Zasada, którą warto zapamiętać: raportowanie jest wczesne, merge nigdy. Skille nakładają labele i publikują review, gdy tylko skończą pracę — nie czekając na CI. Ale merge wymaga, żeby bramki były naprawdę zielone; lokalna walidacja jest dowodem tego przebiegu, nigdy substytutem branch protection.

7a. Corrections log — co zapisałem źle i jak to wyszło

Log nauki jest wart tyle, ile jego wiarygodność. Te wpisy przeszły review, review je obalił dowodem i zostały poprawione — to jest wzorzec, nie wstyd.

● PR #5

1 · Experiment 001 sklejał dwa różne przebiegi

Było: jedna lista obserwacji bez wskazania, skąd pochodzi która — „claim na Issue" obok „odrzucone approve", jakby to był jeden przebieg.
Jest: Goal mówi wprost, że opisane są dwa przebiegi, a bullety noszą swój numer — Issue #2 → PR #3 dla claimu, PR #4 dla reszty.
Jak wyszło: review sprawdziło każdą obserwację osobno i zobaczyło, że przebieg PR #4 nie miał żadnego Issue. Oba zdania były prawdziwe — fałszywa była sugestia, że pochodzą z jednego runu.

2 · „claims prevented concurrent agents" — wniosek bez obserwacji

Było: claimy zapobiegły równoległej pracy agentów.
Jest: claimy były nakładane i zwalniane wokół każdego etapu; to mechanizm, który ma temu zapobiegać, ale kolizji nie było.
Jak wyszło: nikt nigdy nie próbował przejąć tego PR — więc nic nie zostało powstrzymane. Zdanie opisywało intencję projektu jako zaobserwowany skutek.

3 · „Each skill claimed the PR" — nadmierne uogólnienie

Było: każdy skill claimował PR assignee'em, labelą in-progress i komentarzem.
Jest: claimuje tylko om-auto-review-pr; om-open-pr i om-approve-merge-pr działają na PR bez brania locka.
Jak wyszło: timeline PR #4 pokazuje pięć labeli nałożonych bez assignee, a dopiero potem zdarzenie assigned razem z in-progress. Ironia: to zdanie napisał agent, poprawiając poprzedni błąd — dlatego re-review po poprawce nie jest formalnością.

4 · „Human relay is the orchestration model” — prawda historyczna, nie pełny model OM

V6: aktualny diagram mówił HUMAN → skill → HUMAN → skill, a om-auto-fix-issue był tylko hipotezą.
V7: Lessons 1–4 pozostają human-relayed, ale Lesson 5 zaobserwowała om-auto-fix-issue jako flow runner, który sam sekwencjonuje bug companions.
Dowód: plain brief utworzył Issue #7, a późniejszy run przeszedł verify → root-cause → fix → open-pr → review bez ręcznych wywołań pośrednich.

5 · „Branch creation is an OM process gap” — zbyt szerokie uogólnienie

V6: brak automatycznego tworzenia brancha był opisany jako luka SDLC.
V7: to luka manualnego branch-driven path w tym labie. W issue-driven bug orchestration Lesson 5 flow runner utworzył isolated worktree i branch po triage.
Dowód: branch fix/issue-7-readme-purpose-and-navigation powstał automatycznie i został posprzątany po runie.
Reguła wyciągnięta z corrections: każde twierdzenie w logu musi dać się przypiąć do dowodu — numeru PR, Issue, commita albo timeline'u. Jeśli nie potrafisz wskazać dowodu, wpis należy do ◌ not tested, a nie do ● observed. Sekcja Observed ma dlatego klikalne numery.

post-Lesson 5 correction
A · Repo / coverage gaps — czego ten lab nadal nie ma

4 · Branch-driven operator housekeepingManualny path nadal wymaga świadomego branch setup, sync/prune i lokalnego cleanup. Lesson 5 pokazała, że issue orchestrator umie własny worktree/branch lifecycle — nie oznacza to automatyzacji każdego direct-branch runu.
B · Actual OM process / documentation questions
5 · Mandatory tests vs docs-only repositoriesom-fix wymaga regression tests bez wyjątku, ale w tym repo nie ma test runnera. Lesson 5 musiała zastąpić to git diff --check + manual link/table checks. To realne napięcie kontraktu, warte dalszej obserwacji.
